# 开发客户端冻结快照与 2026-10-21 崩溃定位

## 本次崩溃的证据

报告为 `neoforge-1.21.1/run/crash-reports/crash-2026-10-21_22.25.58-server.txt`，游戏时间为北京时间 2026-10-21 22:25:58。

该报告明确记录：

- 异常为 `NoClassDefFoundError: com/example/examplemod/zones/match/MatchSpectatorService$State`，底层为同名 `ClassNotFoundException`。
- 调用链为 `MatchSpectatorService.death:73 → MatchService.onDeath:334 → CommonHooks.onLivingDeath → ServerPlayer.die → EntityPlayerMPFake.die`。
- 被更新的是 Carpet 假人 `PUBG_540b3fc_072`，报告的死亡更新路径包含溺水伤害，并未经过手雷释放、爆炸、烟雾或闪光的代码。
- 源码 `MatchSpectatorService.java` 中的 `State` 定义存在；诊断时 `build/classes/java/main` 中对应编译类缺失，而旧游戏进程仍直接使用该动态输出目录。该时段有失败的增量编译记录。

因此，报告直接证明的是开发运行目录中延迟加载的内部类缺失。运行中的客户端继续读取正在被编译器替换的目录，与“外层类已经加载、内部类随后找不到”的表现一致。玩家当时持有手雷不能将这份堆栈归因为手雷功能；也没有用捕获异常后继续运行来掩盖问题。

## 保留原启动入口

继续双击或执行 `scripts/run-client.bat`。

新入口先运行 `prepareClientSnapshot`，其依赖 ModDevGradle 自带的 `createClientLaunchScript`。官方任务会先完成编译、资源处理、游戏参数准备和启动脚本生成；任何失败均立即停止，不启动旧半成品。

准备成功后，在 Gradle 持有本项目构建锁期间，将下列完整输出冻结到工作区 `.runtime/client-snapshots/<唯一ID>/build/`：

- `classes/java/main`：所有编译类，包含内部类。
- `resources/main`：资源与生成的 `META-INF/neoforge.mods.toml`。
- `moddev`：官方启动脚本、JVM/程序参数、legacy classpath、日志配置和本项目生成的 Minecraft/NeoForge JAR。

冻结器只改写副本中的项目 `build` 路径，保留官方启动器原有 JVM、模块、模组文件夹、游戏目录和依赖参数。Windows 普通路径、Java 参数文件中的双反斜杠和正斜杠形式均会改写。启动前检查文本参数不再引用原 `build` 目录，并要求模组文件夹参数指向快照中的类和资源。

随后原入口执行这份冻结的官方启动脚本。后续编译或 `clean` 只影响原 `build`，不会移除已启动游戏使用的类。存档、配置、模组目录和游戏工作目录仍是原有 `neoforge-1.21.1/run`。

每次启动有独立请求文件和独立快照，不覆盖正在运行的快照。`manifest.json` 最后才写入 `complete=true`，包含每个文件的源哈希和冻结后哈希；复制前后还会重验源文件数量及哈希，以拒绝复制过程中被外部编译器改写的输出。启动器不会自动删除旧快照，也不会停止已运行的游戏进程。

## 不启动游戏的检查入口

```powershell
scripts/run-client.bat -PrepareOnly
```

或只调用准备任务：

```powershell
cd neoforge-1.21.1
.\gradlew.bat --offline --no-configuration-cache --console=plain prepareClientSnapshot
```

这两种命令只编译、冻结和核对文件，不启动 Minecraft。`-PrepareOnly` 通过原启动入口验证完整流程。
